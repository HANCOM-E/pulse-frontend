# 감정 태깅 평가셋 라벨링 가이드

`docs/tagger-validation.md` §5가 적어둔 두 한계를 이번에 걷어내려는 것이 목적입니다.

- **평가셋이 합성 데이터입니다** → 배포 실사용 소감으로 교체·보강
- **라벨러가 1명입니다** → 팀원 1명과 교차 검증

Refs #223

---

## 1. 라벨 기준

`docs/tagger-validation.md` §2 「라벨링 기준」을 **그대로** 씁니다. 여기서 새로 만들지 않습니다. 기준이 두 벌이 되면 기존 182건과 새 데이터를 같이 놓고 볼 수 없습니다.

요약하면 셋입니다.

| 규칙                                                  | 예시                                           |
| ----------------------------------------------------- | ---------------------------------------------- |
| **마지막 절이 결론** — `~는데`/`~지만` 뒤를 따름      | `설명은 좋았는데 예제가 부족했어요` → **NEG**  |
| **NEU는 감정이 없을 때만** — 질문·사실 진술·판단 유보 | `40분 정도 걸렸습니다` → **NEU**               |
| **욕설은 감정과 무관** — `toxic`은 별개 불리언        | `개같이 어려웠지만 배운 건 있습니다` → **POS** |

### 이번에 추가로 정해야 하는 것

실사용 데이터에는 합성 데이터에 없던 모양이 나옵니다. 판단이 갈리면 아래를 따르고, **여기에 없는 새 유형이 나오면 이 문서에 항목을 추가한 뒤 둘 다 그 기준으로 다시 봅니다.**

| 유형                               | 처리                        | 이유                                               |
| ---------------------------------- | --------------------------- | -------------------------------------------------- |
| `ㅋㅋ`·`ㅎㅎ`만 있는 문장          | 사람이 읽은 대로 (보통 POS) | 모델이 못 보는 건 모델 문제지 라벨 문제가 아닙니다 |
| 요청·제안 (`~해주시면 좋겠어요`)   | **NEU**                     | §2 「판단 유보」. 개선 요청은 불만과 다릅니다      |
| 한 글자·의미 없는 입력 (`ㅇ`, `.`) | 평가셋에서 제외             | 분류 대상이 아닙니다. 비고 열에 `제외` 표시        |
| 오탈자로 뜻이 안 통하는 문장       | 평가셋에서 제외             | 사람도 못 읽으면 정답이 없습니다                   |

## 2. 절차

### ① 나누기 — 라벨을 보기 **전에**

수집본을 튜닝/홀드아웃으로 먼저 쪼갭니다.

```
docs/tagger-eval/real-tuning-01.txt
docs/tagger-eval/real-holdout-01.txt
```

**라벨을 붙이고 나서 나누면 안 됩니다.** 어려운 문장을 무의식적으로 한쪽에 몰게 됩니다. 순서를 섞은 뒤 앞에서부터 2:1로 자르는 방식이면 충분합니다.

파일명에 `tuning`/`holdout`이 들어가야 합니다. `npm run tagger:eval`이 파일명으로 세트를 가릅니다.

### ② 독립 라벨링

두 사람이 **서로 보지 않고** 같은 파일에 라벨을 답니다. 사본을 각자 하나씩 가집니다.

```
real-tuning-01.한윤지.txt
real-tuning-01.<팀원>.txt
```

라벨링 중에는 상의하지 않습니다. 상의하면 한 명의 판단이 두 번 세어질 뿐이라 교차 검증이 아니게 됩니다.

**4번째 열(배포예측)을 보지 마세요.** 모델이 뭐라고 했는지 알고 라벨을 달면 모델 쪽으로 끌려갑니다. 가릴 수 있으면 가리고 하세요.

### ③ 불일치만 합의

두 파일을 대조해 다른 줄만 모읍니다. 그 줄만 놓고 이야기해서 하나로 정합니다.

합의가 안 되는 줄은 **억지로 정하지 말고 제외**합니다. 두 사람이 못 정하는 문장은 정답이 있다고 보기 어렵고, 그런 줄을 넣으면 모델을 정답 없는 문제로 채점하게 됩니다.

### ④ 불일치율 기록

**이 숫자가 결과물의 일부입니다.** 버리지 마세요.

| 항목          | 기록할 것                        |
| ------------- | -------------------------------- |
| 전체 불일치율 | 몇 건 중 몇 건                   |
| 클래스 쌍별   | POS↔NEU / NEU↔NEG / POS↔NEG 각각 |
| 제외한 건수   | 합의 실패 + 대상 아님            |

불일치율은 **모델 성능의 상한을 알려줍니다.** 사람 둘이 15% 갈리는 데이터에서 macro F1 0.95를 목표로 잡는 건 의미가 없습니다. 특히 POS↔NEU 경계가 얼마나 흐린지가 `docs/tagger-validation.md` §4에서 NEU 재현율이 0.500으로 낮았던 게 모델 탓인지 문제 탓인지를 갈라줍니다.

## 3. 측정

라벨링이 끝나면 합의본만 `docs/tagger-eval/`에 남기고 개인 사본은 지웁니다.

```powershell
npm run tagger:eval                    # 세트별 macro F1 + 혼동행렬 + 오분류 목록
npm run tagger:eval -- --sweep         # τ 스윕 (튜닝셋만)
```

### 봐야 할 것

1. **세트별 macro F1** — 합성 182건 대비 얼마나 떨어지는지. 떨어지는 게 정상입니다. §5가 예고한 대로입니다.
2. **오분류 목록의 `m=` 값** — `|m|`이 크면 확신에 찬 오답이라 τ로 못 잡습니다. 작으면 τ 조정으로 잡힙니다. **이 비율이 다음 대책을 정합니다.**
3. **「브라우저 예측과 대조」 절** — 불일치가 나오면 라벨 문제가 아니라 실행 환경(WebGPU vs CPU) 차이입니다. 별도 이슈로 뺍니다.

### 하지 말 것

- **홀드아웃으로 τ를 고르지 마세요.** 고르는 순간 홀드아웃이 아닙니다. `--sweep`은 기본값이 튜닝셋 전용입니다.
- **스윕 최고점을 그대로 채택하지 마세요.** 최고점 위치는 표본이 조금만 바뀌어도 크게 움직입니다(§3에서 122건→134건에 최적 τ가 1.35→1.70). 동률 구간 안쪽을 고릅니다.
- **결과를 보고 대책을 즉흥으로 고르지 마세요.** 손사전 중재는 이미 측정해서 기각했습니다(#223 본문). 새 대책도 같은 방식으로 숫자를 내고 판단합니다.

## 4. 알아둘 것

- `lib/tagger/tagger.js`는 스파이크(`감정모델/tagger.js`)의 복사본입니다. **직접 고치지 마세요**(`lib/tagger/index.ts` 주석). 임계값을 바꿔야 하면 스파이크에서 바꾸고 두 벌을 같이 맞춥니다.
- `docs/tagger-validation.md`의 기존 기록은 **지우지 않습니다.** 그 시점의 사실입니다. 새 측정은 새 절로 덧붙이고, 뒤집힌 결론이 있으면 뒤집혔다는 사실과 이유를 씁니다.
- 하네스는 로짓을 `docs/tagger-eval/.logits-cache.json`에 캐싱합니다. 모델 파일이나 토크나이저를 바꿨으면 `--no-cache`로 한 번 밀어야 합니다.
